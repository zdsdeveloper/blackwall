# NetWatch — Design Spec

**Branch:** `netwatch` (off `7a2e6d2`). `master` stays v1 and is the only branch
ever submitted to the Omarchy marketplace.

## What this is

The Blackwall holds back what is on the other side. NetWatch is the agency that
maintains the wall. It is a root daemon that enforces a domain blocklist and
watches its own artifacts for tampering.

It is a **commitment device, not a security control.** The operator has root.
Every mechanism here is defeatable by a determined, informed person at the
keyboard. The design goal is to make defeat *slow, deliberate and memorable*
rather than reflexive — friction, not enforcement.

## Scope boundary

NetWatch polices the wall, not the net. It watches only its own artifacts:

- the blocklist
- the managed region of `/etc/hosts`
- the Zen policy file
- its own unit file and socket

It does not log browsing, does not watch general filesystem activity, does not
inspect traffic, and does not care what else happens on the machine. This is
both the lore-correct behaviour and a deliberate privacy boundary: a tool that
feels like surveillance gets uninstalled.

## Decisions already made

| Decision | Value | Rationale |
|---|---|---|
| Removal model | Delay-based | Operator has root; a secret buys nothing |
| Separate admin account | No | Rejected — cost outweighs benefit |
| Blocklist default | Empty | Domains added over time, by hand |
| Additions | Instant, irreversible within delay window | The asymmetry is the product |
| Removals | 24h delay, cancellable, visible countdown | The wait is the whole mechanism |
| Language | Python 3, stdlib only | 3.14.7 present; matches existing file-guard |
| Blocklist in git | **Never** | Public repo under the operator's real name |
| Review partner | `agy -p --effort high` | Second model on root-side code |

## Threat model

The adversary is the operator at 2am, low deliberation, high motivation, acting
on reflex. Not an attacker. Specifically **not** defended against: another user
with root, physical access, or the operator acting with patience and intent.

## Environment (verified 2026-09-02)

- Zen is `zen-browser-bin` 1.21.16b-1 from the AUR, native at
  `/opt/zen-browser-bin`. Not Flatpak.
- **Zen's build sets `MOZ_SYSTEM_POLICIES: true`.** Confirmed by extracting
  `modules/AppConstants.sys.mjs` from `/opt/zen-browser-bin/omni.ja`.
- `EnterprisePoliciesParent.sys.mjs::_getLocalConfigurationFile()` checks
  `SysConfD/policies/policies.json` first and **returns early if it exists** —
  it does not merge with `<installdir>/distribution/policies.json`.
- `SysConfD` is `/etc/<MOZ_APP_NAME>`. `application.ini` has `RemotingName=zen`,
  so the path is expected to be `/etc/zen/policies/policies.json`. **Not yet
  verified empirically** — Task 4 verifies it via `about:policies` before relying
  on it.
- The package already ships `/opt/zen-browser-bin/distribution/policies.json`
  containing `DisableAppUpdate: true` and `DefaultSerialGuardSetting: 3`.
  Because the system file overrides rather than merges, **these two policies must
  be carried forward** into our file or they are silently lost.
- `/etc/pacman.d/hooks/` exists and is admin-owned — hooks placed there are not
  package-managed and survive upgrades. (`/usr/share/libalpm/hooks/` is not.)
- `/etc/hosts` is 4 lines, stock.
- systemd 261. Python 3.14.7.

## Provenance: drift vs breach

The operator updates the system through the Omarchy bar updater, rarely by hand.
A package upgrade replacing a protected file is **drift** and must be repaired
silently. A hand edit is **breach** and escalates.

Omarchy already solves this exact problem for itself:
`/usr/bin/omarchy-update-pacman-guard` stops direct `pacman -Syu` from bypassing
the updater by reading `/proc/$PPID/cmdline`, and the sanctioned path marks
itself with `OMARCHY_UPDATE_PACMAN=1`.

NetWatch uses the same idea, more directly:

1. **Primary:** a pacman hook pair in `/etc/pacman.d/hooks/` marks a sanctioned
   window — `PreTransaction` writes `/run/blackwall/pacman-window`,
   `PostTransaction` removes it and triggers an immediate re-assert.
2. **Fallback:** `/var/lib/pacman/db.lck` exists → a transaction is live.
3. Otherwise → breach.

A false-positive breach that locks the screen for 20 minutes during routine
maintenance is the single failure most likely to make this tool resented and
removed. The hook exists to make that impossible.

## Architecture

Additions cannot be made by the user writing to the blocklist — it is root-owned
and (once armed) append-only. All mutation goes through a unix socket at
`/run/blackwall/netwatch.sock`; the daemon is the only writer. That is what lets
the daemon enforce "adding is instant, removing is slow" as a property of the
system rather than a convention.

```
netwatchctl ──unix socket──> blackwall-netwatch (root)
                                  │
                                  ├── blocklist   /var/lib/blackwall/blocklist
                                  ├── ledger      /var/lib/blackwall/ledger.jsonl
                                  ├── hosts       managed region in /etc/hosts
                                  └── zen policy  /etc/zen/policies/policies.json
```

## Phasing

Each phase is a separate plan and leaves working software.

| Phase | Plan | Deliverable |
|---|---|---|
| 1 | `netwatch-core` | Working wall, CLI only. Add-only, no removal. Breaches recorded, not punished. |
| 2 | `netwatch-delay` | 24h removal state machine + breach escalation ladder + lock bridge |
| 3 | `netwatch-ui` | Bar widget and window in the Blackwall visual language |

Phase 1 deliberately ships **no removal path at all** and **no punishment**. It
is safe to run while still being built, and it protects from day one.

## Breach escalation ladder (Phase 2)

1. **First breach in a window** — typed-phrase challenge, confirm button disabled
   for 15s. Most urges do not survive being made to type something.
2. **Repeat breach** — Blackwall lock, 15–20 minutes. Reuses the existing lock
   screen and its `breach → press → surge → shatter` vocabulary.
3. **Service killed or masked** — lock engages on next login, daemon re-arms.

Root cannot call the user session's Quickshell IPC directly. The daemon writes a
penalty file; the plugin's existing `GuardedFile` already watches for external
changes and engages the lock. No new privilege bridge.

## Non-goals

- Blocking on any device other than this machine. Phones are handled already
  (iOS: vow + greyscale; Android: BlockNSFW with a discarded random PIN).
- Defeating a VPN, direct-IP access, or a second browser installed on purpose.
- Any of this reaching the marketplace.
